# shopping-aggregator, Config

A run needs facts about the buyer that do not change from one purchase to the next: the market, where things ship, which memberships and store credit can be used, where the agent may check out, and what the buyer wants by default. This file defines where those facts live and in what shape. It is the only definition. `tools/config_schema.py` implements the tables below, and the doctor (`scripts/verify_config.py`), the ledger writer (`scripts/ledger.py`), `tools/verify_matrix.py` and the tests all call it, so there is one answer to "is this config valid", not one per caller.

A **config root** is one person's settings plus their run data. Real roots live only in a separate, versioned, PRIVATE companion repository. This public repository ships the schema, the tools and synthetic examples generated by `tools/make_fixtures.py` (`skills/shopping-aggregator/config/`). A fact this file has no field for is not stored anywhere until it has one: add the field here, in `tools/config_schema.py` and in the generator, then store it. It never goes into an agent memory, a script constant, a command-line default or a free-text note, because each of those is a second copy that the doctor cannot see and a switch of person does not move.

## Layout

```
<root>/                          one person
  README.md                      required; generated pointer back to this file
  .gitignore                     required; secrets gate
  profile.json                   required; who is buying (schema below)
  registry.json                  required; which optional sources this root has set up
  reference/                     private tables a profile points at (optional)
  data/                          required; everything a run produces, all versioned
    metrics/live-runs.jsonl      what runs observed about sources (SKILL.md Step 7)
    metrics/live-runs.legacy.jsonl  frozen pre-schema rows that could not be reconciled (optional)
    purchases.jsonl              every order action taken on the buyer's instruction
    evaluation/runs/<run-id>/    scenario-eval transcripts and results
    cache/                       rebuildable, and versioned too: the private writer refuses ignored paths
  people/<id>/                   another person's complete root, same layout
  tools/<slug>/                  required directory; per-tool templates (env.template, claude.json.template)
  secrets/                       required directory; credentials, ignored by default
```

Settings sit at the root and everything a run produces sits under `data/`. `people/<id>/` is a complete root of its own: selecting it moves the profile and both ledgers, and the evaluation runs and the cache too when it is selected through the environment (see Switching). Apart from an optional `.companion` ownership marker and the generated READMEs, nothing else belongs in a root.

## Discovery

`scripts/init_config.py`, `scripts/verify_config.py` and `scripts/ledger.py` choose a root in this order and print the one they used:

1. `--out <dir>` (init) or `--config-dir <dir>` (doctor and ledger).
2. `$SHOPPING_AGGREGATOR_CONFIG`.
3. `$SHOPPING_AGGREGATOR_CONFIG_DIR`, an accepted alias.
4. The pinned resolver `guards/tools/datadir.py`: `$SHOPPING_AGGREGATOR_DATA_DIR` (its parent when it ends in `data`), then the sibling `shopping-aggregator-config/` next to this repository, then `~/.shopping-aggregator-config/`, then `~/.shopping-aggregator-data/`.

An explicit selection never falls through. A selection that is empty (`--config-dir ""`, or a variable exported empty) is an error, and so is a selected directory that does not exist, except for `init_config.py`, which creates it. The sibling counts only when it proves it belongs to this skill, through an origin URL named `shopping-aggregator-config` or a `.companion` file whose first line is `shopping-aggregator`. When nothing resolves, the doctor exits 1 and `init_config.py` creates `~/.shopping-aggregator-config/`. There is no in-repository fallback, no XDG directory and no vendored copy of the resolver. [`guards/COMPANION.md`](guards/COMPANION.md) is the contract for the companion repository itself.

`$SHOPPING_AGGREGATOR_DATA_DIR` and `~/.shopping-aggregator-data/` are data-only locations from before config roots existed. The resolver still finds them, but they have no `profile.json` and no `data/` of their own, so the doctor reports them NOT READY and the ledger writer refuses them. Migrate their contents into a root's `data/`.

The `tools/` commands (evaluation runs, the GitHub-activity cache, `refresh_priority`, `verify_matrix`) do not take `--config-dir`; they follow only the environment through the resolver, in which `$SHOPPING_AGGREGATOR_DATA_DIR` outranks `$SHOPPING_AGGREGATOR_CONFIG`. So the doctor and the ledger writer both refuse to proceed when `$SHOPPING_AGGREGATOR_DATA_DIR` is anything other than the selected root's `data/`, or when `$SHOPPING_AGGREGATOR_CONFIG` or `_CONFIG_DIR` names a different root than `--config-dir`: either would send those tools to another person's data. A selection variable that is set but empty, or that names a directory that does not exist, stops every command, `tools/` included, because the resolver would skip it and fall through to the next candidate. Quote Windows paths or write them with forward slashes: Git Bash drops the backslashes of an unquoted one.

The commands use this repository's `.claude-plugin/plugin.json` and the pinned `guards/` submodule wherever they are called from. Run `git submodule update --init --recursive guards` after cloning and after every pull that moves the `guards` pointer; the commands refuse a kit that differs from the pinned commit.

## profile.json

| Field | Type | Required | Meaning |
|---|---|---|---|
| `schema_version` | integer `1` | yes | Profile schema version |
| `profile_id` | kebab-case id | yes | Stable id; every purchase row carries it and the report header names it |
| `label` | string | yes | Short human label for reports, not a legal name |
| `market.country` | ISO 3166-1 alpha-2 | yes | Buying market; selects the domain set and the BigGo region |
| `market.currency` | ISO 4217 | yes | Currency the report converts into |
| `market.locale` | `xx-YY` | yes | Page language and number format |
| `ship_to.zip` | postal code; in a US market `12345` or `12345-6789` | yes | Store-zoned prices, local stock and tax |
| `ship_to.state` | two letters | in a US market | The row to read in `skills/shopping-aggregator/reference/data/us-sales-tax.json`; elsewhere an optional region code |
| `ship_to.city` | string | no | Pickup and local-store reads |
| `ship_to.effective_from` | `YYYY-MM-DD` | yes | When this destination became current |
| `memberships[]` | array of objects | yes, may be empty | Paid programs held; see below |
| `not_held` | kebab-case ids | no | Programs confirmed not held, so member-only prices become conditional rows |
| `store_credit` | kebab-case ids | no | Kinds of stored value on the buyer's accounts, such as a gift card; never an amount |
| `purchase_defaults.subscriptions` | `accept-fee-free`, `ask` or `decline` | yes, no default | When the cheapest stack is a subscription cancellable without fee: buy it on announcement, ask first, or leave subscriptions out of the stack. Init leaves it blank so that nobody's commitment policy is chosen for them |
| `purchase_defaults.subscription_interval` | `page-default`, or `N-days` / `N-weeks` / `N-months` | yes | Interval when the buyer names none; `page-default` is the page's own |
| `risk.marketplace_min_rating_pct` | number 0 to 100 | no, default 95 | Marketplace seller cutoff (Step 6) |
| `risk.marketplace_min_ratings` | integer | no, default 500 | Marketplace seller cutoff (Step 6) |
| `risk.deep_depth_usd` | number | no, default 500 | Ticket size that earns deep depth (Step 2) |
| `accounts[]` | array of objects | no | Retailer accounts; see below |
| `home_stores[]` | `{retailer, store}` | no | Store ids for zoned prices and pickup |
| `travel` | object | no | `home_airports` (IATA codes), `cabin` (`economy`, `premium-economy`, `business`, `first`), `checked_bags`, `payment_currency`, `hotel_adults` |
| `off_limits` | kebab-case ids | no | Platforms the agent must not automate while logged in |
| `forwarders[]` | array of objects | no | Parcel forwarders; see below |
| `preferences` | object of kebab-case category to text | no | Buying preferences (sizes, scent, firmness) in words; a bare date is refused |

Every object has a closed set of fields: an unknown field anywhere is refused, so a new kind of fact needs a schema change first.

A `memberships[]` entry has `program` (kebab-case id, required), `tier` (kebab-case), `perks` (kebab-case ids such as `free-shipping`, `member-price`, `cash-back`), `cash_back_pct` (0 to 100) and `confirmed_on` (date, required). The date matters: a membership is a fact about a moment, and a report that relies on one older than the run should say so.

An `accounts[]` entry has `retailer` (the lowercase host, such as `example.com`, required), `checkout` (required), `session` and `identity`. The entry applies to exactly that host. `checkout` says who may submit an order there: `agent` (the agent may drive checkout after an explicit instruction), `owner-browser` (the retailer blocks automation, so the agent prepares the cart and the owner submits in their own browser) or `none` (no orders through this account at all, neither submitted nor prepared). A retailer without an entry, or a run without a conforming profile, is treated as `owner-browser`. `session` names a session-store group as `<store>:<group>`, for example `session-store:example`; cookies stay in that store and never enter the root. `identity` is a label for which of the person's identities owns the account, never the address itself.

A `forwarders[]` entry has `name` (kebab-case, required), `zone`, `duty_inclusive` (Boolean) and `rate_table`, a path relative to the root (usually `reference/forwarder-<name>.json`). A forwarder's rate table has no public source, so it stays private next to the profile that uses it, in one shape for every forwarder so a landed-cost step reads any person's table the same way:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `schema_version` | integer `1` | yes | Table schema version |
| `name` | kebab-case | yes | Must equal the profile's `forwarders[].name` |
| `currency` | ISO 4217 | yes | Currency of every rate |
| `duty_inclusive` | Boolean | yes | Duties and import taxes are inside the rate, so the duty table is not applied on top; must agree with the profile entry |
| `zone_by` | `zip-first-digit` | yes | How a destination maps to a zone |
| `zones` | object of zone id to postal-code prefixes | yes | The profile's `zone` must be one of these, and the one whose prefixes contain its ship-to ZIP |
| `classes` | object of goods class to zone id to tiers | yes | Each tier is `{min_kg, max_kg, rate_per_kg}`; `max_kg` is `null` for the open top tier |
| `volumetric_divisor_cm` | number | no | Volumetric weight = L x W x H (cm) / divisor; bill the larger weight |
| `min_billable_kg` | number | no | Smallest billable weight |
| `notes` | string | no | Surcharges, transit time, liability |
| `source`, `verified_date` | string, `YYYY-MM-DD` | yes | Where the table came from and when it was last confirmed |

The doctor follows `rate_table` only when it is a plain relative path that stays inside the root, and fails when the file is missing, malformed, or disagrees with its profile entry. Example: [`forwarder-table.example.json`](skills/shopping-aggregator/config/forwarder-table.example.json).

`purchase_defaults` holds only the answers the guardrails leave to the buyer. Stacking every eligible discount, clipping coupons, checking each discount line on the final page and asking before any other commitment are guardrail #16 and CONSTITUTION V.4, the same for every buyer, so the schema has no field that could turn them off. An instruction in the current conversation overrides a default for that run only and does not edit the file.

The full example, with synthetic values only, is [`skills/shopping-aggregator/config/profile.example.json`](skills/shopping-aggregator/config/profile.example.json).

### What a profile never holds

A profile holds what changes a price or a route, not who the person is: no street address, phone number, email address, date of birth, card, account or routing number, credential, balance, passport or license number. Because every object is closed, the only free keys are preference categories, and ordinary category words stay usable there, including ones that contain a sensitive word (rolling-pin, passport-cover, credit-card, no-store-card). The schema refuses this data in two ways:

- **by shape, in every value and every key**: email addresses; digit runs of nine or more digits once separators are removed (phone, card, account and routing numbers); street addresses (a house number, a name and a street suffix, the suffix after the number in some countries, and PO boxes); long mixed letter-and-digit runs that look like tokens or cookies; and a preference that is only a date;
- **by name**: keys whose words, read together, label a credential or an identity number (password, PIN, CVV, SSN, IBAN, routing number, passport number, card or account number, API key, date of birth). A category that merely contains such a word is not refused.

A balance or a date of birth written as plain words cannot be recognised by its shape, so never put one in free text. Checkout never types contact or payment data either ([purchase execution](skills/shopping-aggregator/reference/purchase-execution.md)). The doctor reports the field path of every refusal and never the value; a key that is itself unsafe to print appears as `<key>`.

## registry.json

```json
{
  "schema_version": 1,
  "skill": "shopping-aggregator",
  "tools": [
    {"slug": "biggo-mcp", "installed": true, "transport": "stdio", "notes": "free text"}
  ]
}
```

`schema_version` is the integer `1`, `skill` must equal the plugin name and `tools` is required even when empty. Each tool needs a kebab-case `slug` and a Boolean `installed`; `transport` is one of `stdio`, `http`, `sse`, `rest`, `python-lib`. A tool that needs credentials gets `tools/<slug>/env.template` (and `claude.json.template` for an MCP server) with `<UPPER_SNAKE>` placeholders, and its real values go to `secrets/<slug>.env`, UTF-8 without BOM. Example: [`skills/shopping-aggregator/config/registry.example.json`](skills/shopping-aggregator/config/registry.example.json).

## Ledgers

Both ledgers are append-only JSON Lines under `<root>/data/`, and `scripts/ledger.py` is their only writer. Pass the row on standard input, read as UTF-8 whatever the console code page; `--row '<json>'` works only in POSIX shells, because Windows PowerShell 5 strips the quotes inside it. A row file, if you use one, must live outside this repository: the writer refuses one inside it, and a `row.json` at this repository's root is sealed.

```bash
python scripts/ledger.py append live-runs --row-file - --config-dir <root> <<'EOF'
{"domain": "example-domain", "source": "example-source", "outcome": "verified", "detail": "...", "user_correction": null}
EOF
python scripts/ledger.py check --config-dir <root>
```

In PowerShell, pipe the row: `'{"domain": ...}' | python scripts/ledger.py append live-runs --row-file - --config-dir <root>`.

The writer stamps `ts` when the row has none (a `ts` that is present must be an ISO-8601 date or date-time), validates the row before opening anything and refuses even what the checker only warns about, proves the destination is in a versioned PRIVATE repository, and replaces the file atomically under a lock kept in that repository's git directory, so concurrent appends cannot drop each other's rows. It escapes the three characters that some readers treat as line breaks (U+2028, U+2029, U+0085), so every row stays one line. A row that is invalid is fixed and appended again; any other refusal is reported in the reply, and nothing is written anywhere else (CONSTITUTION II.5). `check` reports invalid rows and exits 0 when no root is initialized at all.

`data/metrics/live-runs.jsonl` requires `ts` (ISO-8601 date or date-time), `domain`, `source`, `outcome`, `detail` (non-empty strings) and `user_correction` (null or a string). `outcome` is one of `created`, `verified`, `unverifiable`, `dead`, `fallback_used`, `price_mismatch`, `coupon_fake`, `coverage_gap`: the writer refuses any other value, and `verify_matrix` only warns about one in an old row. A `coverage_gap` row requires a `gap_reason` from the [refresh protocol](skills/shopping-aggregator/reference/refresh-protocol.md#feedback-loop). Example: [`live-runs.jsonl.example`](skills/shopping-aggregator/metrics/live-runs.jsonl.example).

When a field becomes required after rows were written without it, the old rows are reconciled by hand against the private evidence and fixed in place. A row whose value cannot be recovered, because its own record does not state it, moves to `data/metrics/live-runs.legacy.jsonl` instead of being given a guessed value. That file is frozen: no tool reads or writes it, and a row goes back to `live-runs.jsonl` only once it has been reconciled.

`data/purchases.jsonl` has a closed set of fields. Required: `ts`, `profile_id`, `retailer`, `order_ref`, `item`, `path` (`one-time`, `subscription`, `multi-pack`), `quantity` (a positive integer), `charged_total` and `status` (`placed`, `cancelled`, `replaced`, `returned`). Optional: `variant_key`, `items_total`, `tax`, `paid_with` (`store-credit`, `card`, `mixed`, `other`), `discounts[]` of `{type, amount, mark}` with `mark` one of `cart_tested`, `unverified`, `expired_failed`, `paid_later`, `subscription`, `replaced_by` and `notes`. Amounts are finite non-negative numbers. A subscription carries `subscription.interval` (`N-days`, `N-weeks` or `N-months`) and, while it is `placed`, `subscription.next_delivery`. Rows are events: a correction appends a `cancelled` row for the original order and a `placed` row for the replacement, and may then append a `replaced` row that links the original to it. Only a `replaced` row names a `replaced_by`, which differs from its own `order_ref`. The row must name the selected root's `profile_id` itself: the writer never fills it in, so one person's order cannot be filed under another person's root by a forgotten selection. Example: [`purchases.jsonl.example`](skills/shopping-aggregator/config/purchases.jsonl.example).

## Storage, secrets and backups

A profile says where a person lives and what they pay for, so the doctor requires the root to sit in a versioned repository whose every fetch and push remote is PRIVATE, proven against the visibility receipt at `~/.pii-guard/visibility.json` (format in `guards/README.md`; it must be under 30 days old). A root that cannot be proven private is NOT READY even when every field is right. The public tool repository never holds a real root: `.dataclass.json` seals the config-root names (`profile.json`, `registry.json`, `people/`, `data/`, `reference/`, `secrets/`, `row.json`) at this repository's root and declares a real-file twin next to every example, and `guards/tools/data_boundary.py` blocks them on commit, push and CI. Below the root, `verify_matrix` (CONFIGROOT, run in CI) refuses any tracked file named `profile.json`, `purchases.jsonl`, `row.json` or `forwarder-<name>.json`, and anything under a `people/` directory.

Generated ignore rules exclude `secrets/*` and credential files from accidental staging, and nothing under `data/`, because the private writer refuses ignored paths; the doctor checks both, probing every path the writers create and every existing file under `data/`. Keep credentials out of version control with a separate backup, or deliberately track selected ones in the PRIVATE companion; an ignore rule does not stop an explicit `git add`. A credential committed there stays in that history, so rotating it means replacing the credential itself. No tool here echoes a secret value.

## First-time setup

```bash
git submodule update --init --recursive guards
python scripts/init_config.py        # reuses the companion it finds, or creates ~/.shopping-aggregator-config
cd <root> && git init && git remote add origin <PRIVATE repository URL>
```

Name the private repository `shopping-aggregator-config` and keep it next to this repository so the resolver finds it by itself; otherwise select it with `SHOPPING_AGGREGATOR_CONFIG`. Refresh the visibility receipt so it lists that repository as PRIVATE. Fill `profile.json` (including `purchase_defaults.subscriptions`) and `registry.json` from the examples, commit them in the companion, and run `python scripts/verify_config.py` until it prints `CONFIG CONFORMS`. `init_config.py` writes the same bytes on every run and skips files that exist unless `--force` is given. Conformance is not proof that a session, an MCP server or a retailer works; those still need a functional read.

## Switching between people

Each root owns its settings and its data. There are two ways to select one, and they reach different things:

```bash
export SHOPPING_AGGREGATOR_CONFIG=~/configs/buyer-a     # this shell: scripts/ AND tools/ follow it
python scripts/verify_config.py --config-dir ~/configs/buyer-b   # this one command only
```

`--config-dir` moves only the `scripts/` command it is given to. The `tools/` commands follow only the environment. An agent's tool calls do not share environment variables, so a run for anyone but the default root passes the same `--config-dir <root>` to every `scripts/` command and sets `SHOPPING_AGGREGATOR_CONFIG=<root>` in the same command line as every `tools/` command (`$env:SHOPPING_AGGREGATOR_CONFIG='<root>'; python ...` in PowerShell).

Inside one companion, add a person with `python scripts/init_config.py --out <companion>/people/<id>`, fill and commit their profile, and select `<companion>/people/<id>` the same way. `python scripts/verify_config.py --all` checks a root and every `people/<id>/` under it, and fails when two roots share a `profile_id`. Leave `SHOPPING_AGGREGATOR_DATA_DIR` unset, or equal to the selected root's `data/`. Every report names the `profile_id` it used, and a purchase row whose `profile_id` differs from the selected root's is refused.

## Changing a profile

Edit the file, run the doctor, commit in the companion. The agent changes a profile only when its owner states a new fact ("I cancelled that membership", "I moved"), sets `confirmed_on` or `effective_from` to the date it was stated, and never infers a change from a page it read.

## Storage lifecycle

`storage.contract.json` maps the companion paths to retention decisions and references this document for their schemas. `scripts/verify_config.py` rejects undeclared root entries as well as invalid fields. PRIVATE storage and Git history do not imply indefinite retention.

The online matrix discards cache keys for repositories no longer referenced, malformed or failed observations, future timestamps, and observations older than seven days before writing the refreshed cache. An inactive `data/cache/` can be removed and rebuilt. Offline verification does not touch it.

Retain live observations and purchases. Keep a legacy ledger only while it has unique facts or corrections awaiting schema reconciliation; preserve those facts and a migration receipt before retiring it. Do not relabel unsupported old outcomes as fresh successful observations. Keep active or selected evaluation evidence, then retire redundant transcripts and checkpoints after its final conclusion and source hashes are retained. Compact lifecycle decisions may be stored in `data/retention/*.json`; they are not a raw-output archive.

The shared storage checker is provided by skill-smith at `skills/skill-smith/scripts/storage_contract.py`; do not copy it into this repository.
